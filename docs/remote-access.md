# Optional remote gateway

Remote access is disabled by default. The local owner service binds only 127.0.0.1:4317. A separate HTTP listener on 127.0.0.1:4318 is the only supported tunnel target. It independently verifies Cloudflare Access JWT signatures, issuer, audience, expiry, token type and invited identity, then applies host user permissions. It has no local-owner session bootstrap. No runtime or database ports are exposed.

## Decision and setup

Cloudflare Tunnel + Access is the initial supported public deployment: an outbound tunnel avoids inbound host firewall openings, Access supplies established identity authentication, and the application still validates signed identities and maintains its own revocable user grants. Tailscale Serve is a strong private-network alternative, but Tailscale identity headers are not accepted as equivalent JWT credentials by this gateway. Generic reverse proxies/OIDC integration need a separate verified identity adapter. No custom login cryptography, cookies scraped from consumer AI subscriptions, URL bearer secrets or anonymous quick tunnels.

1. Create a Cloudflare Access self-hosted application for a domain you control. Configure an identity provider with MFA/passkeys and an explicit allow policy. This requires your account and domain; Relay cannot fabricate them.
2. Create a named Cloudflare Tunnel. Route only that hostname to `http://127.0.0.1:4318`, preserve its public Host header, and finish the ingress list with a deny/404 rule. Never target port 4317, 5432, 11434, 1234 or the Docker socket. Do not enable unprotected alternate ingress.
3. Configure `RELAY_REMOTE_ENABLED=1`, `RELAY_REMOTE_ORIGIN=https://your-hostname`, `RELAY_ACCESS_ISSUER=https://your-team.cloudflareaccess.com`, and `RELAY_ACCESS_AUDIENCE=<application audience>`. These are configuration, not AI credentials. Start the host; gateway setup failure leaves local access usable.
4. From the local owner's Access panel, invite the exact identity-provider email and grant providers, workspaces, computer access and budgets. Chat users default to local AI with no workspaces, no writes, no terminal and no cloud spending. Verified URL access alone does not grant an account.
5. Test an authorized identity, an uninvited identity, incorrect issuer/audience, expired session, account revocation, cross-user ID guessing, mobile approvals, reconnect, Stop and tunnel failure before sharing the URL.

Sessions use Secure HttpOnly SameSite cookies on remote HTTPS, CSRF tokens for mutations and one-hour expiry. JWT identity is verified on each remote request. Revoked users/versions invalidate sessions and cancel tasks. A live SSE stream checks session validity continually and closes no later than the cryptographically verified Access token expiry. Streams are limited to four per user and 32 across the host's listeners. Owner configuration and provider secrets stay local-owner-only. A device is currently represented by a revocable browser session and its user-agent label, not cryptographic device attestation. Revoking one browser session ends its API/stream access; cancelling previously queued tasks requires the user-level revoke/stop control.

## Threat model and limits

Public requests encounter gateway identity verification, host/origin policy, rate/body limits, session/CSRF validation, user policy, schema validation, task budgets and deterministic tools. The gateway is a separate listener in the same modular service, not a separate OS identity. A host-process exploit remains high impact; no production penetration-test claim is made. Deployments need an external edge rate limit and denial-of-service protection. No public deployment was enabled during development.

Local owner access requires a short-lived, one-use pairing code delivered through an OS-account-restricted host file. Loopback HTTP access alone cannot mint an owner session, and the remote listener rejects owner pairing. See [the security model](security-model.md) for source/portable pairing instructions, the upgrade invalidation of older local sessions, and the OS-account boundary. Software running as the same OS account, elevated administrators, and compromised owner credentials remain outside that protection. JWT/JWKS caches must not be mistaken for provider-account revocation; host session/account revocation takes effect independently. No unpriced cloud model is admitted under a strict monetary budget; invited users cannot opt out of their cap.
