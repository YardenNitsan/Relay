## Baseline critique

The running production browser was inspected at 1440×1000 (`output/playwright/refinement-before-desktop.png`). The navy/slate surfaces, Plex typography and connected execution record are coherent. The main weaknesses are compact microcopy, phone navigation relying on a command symbol, hidden compute depth at narrow widths, undersized utility targets, and a spinner-only conversation-loading state. The existing approval identity work should be preserved.

## Direction before implementation

Retain ink `#182b3d`, blue `#2b5f96`, canvas `#f5f7fa`, white `#ffffff`, and the dark navy counterparts already defined in the product. IBM Plex Sans carries conversation and controls; Plex Mono is reserved for code and exact machine values. The memorable element remains the connected execution thread, not decorative cards or gradients.

Desktop: persistent narrow toolbar → centered conversation → anchored composer, with the execution inspector alongside only when requested. Phone: compact header with a named navigation button → one main surface → composer with explicit model and compute controls; secondary surfaces occupy the viewport. Pairing is a separate entry screen before privileged data loads.

Review against the brief: adding a permanent sidebar, stock dashboard panels or glass styling would weaken the conversation-first design. The chosen refinement improves readability, reachability and state feedback while preserving the working product and factual execution records. No new runtime dependencies are required.

## Verification plan

Build and typecheck; frontend unit tests; real API-backed browser tests for pairing, conversation persistence, supervised approvals and diffs, access policy, emergency stop, navigation/focus, skeleton/error states and all responsive controls. Inspect screenshots at desktop/tablet/phone widths and both themes. Run automated accessibility checks, while explicitly avoiding a claim of complete WCAG conformance from automation alone.

## Applied refinement and review

The current Apple layout guidance was rechecked through its [official documentation data](https://developer.apple.com/tutorials/data/design/human-interface-guidelines/layout.json), which identifies a September 9, 2026 revision. Its guidance on layout dimensions, hierarchy, safe areas and progressive disclosure informed Relay's compact navigation and inspector behavior. Native Liquid Glass guidance is not an appropriate material requirement for this browser-based execution product; opaque surfaces preserve contrast for commands and approvals.

- Phone navigation now has a named Menu entry with explicit destinations, 56px menu rows, keyboard containment and focus restoration across successive dialogs. Model and compute selection stay available as the composer changes shape.
- Pairing is a deliberate entry screen before privileged queries. The token is masked, erased after submission, and absent from local storage, session storage and URLs. Invalid tokens produce an actionable error. This interface reflects the actual authentication boundary.
- Conversation loading uses a quiet structural skeleton. A failed load offers a retry, and the original persisted conversation returns. No loading decoration claims that an agent has executed.
- Resource policy separates a draft from the applied host setting. Failed saves preserve the applied label; successful saves survive reload. Custom reserves have explicit limits and a responsive field grid. Runtime allocation is labeled as a runtime report, with unavailable data shown plainly.
- Visual review caught an unfinished reserve layout and a temporary contradictory Saving/Saved state. Both were corrected. Activity labels were increased to 13px with 12px supporting text. Compact-height windows use a smaller, top-aligned welcome surface.
- Screenshots now settle theme transitions before capture. An intermediate transition had made screenshot text look lower-contrast than the actual settled theme; the dark conversation/activity surface also receives an axe scan.

The full 22-scenario Chrome suite passed after these functional changes. It covers eight viewport dimensions from 320px to 1920px, real persistence/tool/approval paths, pairing, draft versus saved policy, invalid reserve input, and reduced-motion keyboard behavior. The test provider is explicitly deterministic; hardware remains observed host telemetry. Ordinary scenarios reuse one legitimately paired session in test-worker memory and pace synthetic scenario admission so production rate limits remain enabled.

After the final readability adjustments, nine affected browser scenarios passed. A further desktop keyboard regression reproduced focus loss when closing a model dialog opened from the command palette. The modal now returns focus to a visible navigation control if its original trigger was removed. All seven refinement scenarios, including that new regression, then passed, as did seven frontend unit tests and the strict production build. There are now 23 browser scenarios in total; the earlier full run contained 22 and the final focused run covered the changed paths.

Production restart review subsequently found a stale-session state: a rejected API request cleared the API module's session, but the successful React Query session still kept private views and polling enabled. The browser now invalidates both layers together, cancels and removes private query state, clears streamed content and requires explicit pairing/reconnection. Session generations reject late responses so a previous session cannot repopulate private content or invalidate a newly paired browser. Four API tests cover invalidation, response races and the distinction between remote account revocation and ordinary permission denial. A real active-session revocation browser test advances the browser clock 30 seconds and observes no automatic API requests before re-pairing. All eight refinement tests and eleven frontend unit tests passed after this correction; the browser suite now contains 24 scenarios.

Artifacts under `output/playwright/` include `refinement-conversation-light.png`, `refinement-conversation-dark.png`, `refinement-phone-light.png`, `refinement-pairing.png`, `refinement-resources-tablet.png`, the eight `relay-WIDTHxHEIGHT.png` views, and both phone approval captures. These browser captures were visually inspected. Native iOS/Android keyboards, screen-reader user testing, and Safari on a physical Apple device remain separate validation work; viewport emulation does not establish those results.

Final integrated verification on 2026-10-06 reran the entire expanded suite against the final built browser: **24 of 24 Chrome scenarios passed in 1.6 minutes**. The latest desktop conversation, 320px phone and tablet resource surfaces were visually inspected again. Windows and native Linux each passed all 249 deterministic tests, including the browser API/session regressions. The compiled production host separately passed actual Ollama write/read/approval acceptance and persistence after restart; those live results do not use the deterministic browser provider.

## Persistent history refinement

The next increment replaces the browser's limited in-memory title filter with authorized PostgreSQL full-text search and exact message links. Conversation lists use stable creation-time pages; the reader replaces bounded 80-message pages instead of accumulating an enormous DOM. Search remains inside the existing progressively disclosed history dialog. Dates now include the year, making long-lived histories unambiguous. See [history design and research](history.md).

Nine new repository/HTTP checks passed, and two new Chrome scenarios passed against 106 clearly labelled fixture conversations, 225 messages and 101 task records. The browser walks beyond the former recent-history limits, opens an old task's real stored activity record, searches an old exact message, and preserves its deep link on reload. Desktop dark and 320px light search surfaces passed axe checks. Visual captures `history-desktop-dark.png`, `history-search-phone.png`, and `history-message-phone.png` were inspected; review prompted a narrow-screen scroll correction and removed redundant floating navigation when the history controls are already visible. Production history data is never replaced by these fixtures.
