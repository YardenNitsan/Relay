# Reviewed offline development images

Provision explicitly with `node --import tsx scripts/provision-development-images.ts all` (or `node`, `python`, `dotnet`). This downloads digest-pinned official base images into the selected local Linux Docker engine and builds a tiny reviewed context. No project files, credentials or host workspace are sent to the build. Build commands have network disabled. Provisioning does not change a running Relay host, install models or publish images.

The report under `output/final-evolution/development-images-*/report.json` records Dockerfile hashes, actual local immutable image IDs and architecture. Configure the relevant `RELAY_SANDBOX_NODE_IMAGE`, `RELAY_SANDBOX_PYTHON_IMAGE` or `RELAY_SANDBOX_DOTNET_IMAGE` with that ID when deliberately starting a host. Do not substitute the temporary human-readable build tag. The engine-resolved image ID can differ from BuildKit's config digest on containerd installations.

Run `node --import tsx scripts/development-language-acceptance.ts output/final-evolution/development-images-latest.json` after provisioning all profiles. It executes actual failing and passing multi-file programs through DockerSandbox. No project code runs on the host. The Node24 supervisor verifies privilege dropping, capabilities, seccomp, no-new-privileges and bounded temporary filesystems before language execution.

The .NET SDK needs its intermediate and binary outputs outside the exchanged text workspace. The native acceptance command directs them to disposable `/tmp`; its NuGet configuration clears online sources. No package restoration from external services is available. The .NET profile permits a bounded64MiB process file size because CoreCLR clips its executable-memory mapping to that limit; other profiles retain1MiB. All retain512MiB RAM, one CPU,64processes,64MiB temporary/workspace mounts, no network, and1MiB per exported UTF-8 file. Write-Xor-Execute remains enabled.

Verified locally: Windows Docker Desktop with Linux/amd64 containers, Node24.21.0, Python3.14.8, .NET SDK10.0.401. Registry ARM manifests alone do not establish native ARM/macOS acceptance. Small program acceptance does not establish medium-sized application builds, optional SDK workloads or package-source policy. The SDK currently reports an offline workload-verification warning; workload installation remains unavailable.

The Dockerfiles pin official Node, Python and Microsoft .NET images. Their existing runtime and distribution notices remain in the base images; the copied Node binary retains its bundled license. Relevant upstream sources are [Node Dockerfiles](https://github.com/nodejs/docker-node/tree/93a7bafc324a85ac1ee461604cff87cffacb6d7a), [Python Dockerfiles](https://github.com/docker-library/python/tree/7cc547b3ff8d45d540cd23144227af126a79d60c), and [.NET Dockerfiles and license](https://github.com/dotnet/dotnet-docker). Building these images does not choose a license for Relay. Redistribution and release notices require their own review before publishing artifacts.
