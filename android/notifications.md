# Private task notifications

Implementation plan (13 October 2026): add an opt-in, encrypted, bounded watch ledger; bind it to the authenticated HTTPS origin, account and saved session; test transition deduplication, expiry and stale-session rejection; connect generic notifications and task-specific authenticated navigation; add a network-constrained periodic worker and foreground event checks; verify tests, lint and installed Android behavior in the coordinated build slot.

Account → Enable task notifications asks Android for notification permission. While enabled, tasks submitted or opened in this app are watched, up to 20 tasks for seven days. Completed, failed and pending-approval changes can notify. Existing completed history does not generate old alerts. Disabling notifications or signing out clears watches, outstanding notifications and scheduled work. A revoked session stops notification monitoring when the next authenticated check detects it. Unreachable hosts do not generate disconnected alerts.

The background monitor uses WorkManager at a minimum interval of 15 minutes. Android battery/network policy can delay it; this is best-effort polling, not push, an exact timer or an always-on LAN connection. Foreground activity events check the affected watched task immediately. No new host service or remote infrastructure is used.

Notification text is generic and hidden on the lock screen. No task objective, result, error, model, host, account, cookie or CSRF token is sent to Android notification text or pending intents. An immutable, explicit activity intent carries only a random local lookup token. Opening it requires secure session restore, the original origin/account/session binding, and fresh authenticated task/conversation reads. There is no approval action on the notification itself.

The encrypted ledger stores only bounded task IDs, transition keys, timestamps and random lookup tokens. Credentials remain in SessionVault. Notification publication and invalidation share a process lock; late worker results cannot publish after logout or account replacement. Workers reauthenticate and confirm account identity; authorization failures invalidate notification state. Ordinary connection failures remain quiet until a later check.

Sources inspected: [WorkManager dependency and CoroutineWorker](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started), [minimum interval and constraints](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work), [Android notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission), [notification construction and privacy](https://developer.android.com/develop/ui/compose/notifications/create-notification). Maintained AndroidX WorkManager 2.12.0 is the only added dependency.

Task reads and notification publication share one coroutine gate across foreground refresh, SSE and the worker. The process lock alone would not order overlapping network responses. Terminal outcomes are sticky in the ledger, so a delayed pending approval cannot replace a completed outcome. The worker still authenticates after tasks settle, allowing later revocation to clear delivered notifications. Expired watches and their notifications are removed; notification timeout is bounded by the watch expiry.
