# Controlled MCP integration

Relay uses the official `@modelcontextprotocol/client` 2.3.1 SDK, pinned to protocol `2026-07-28`, behind a constrained host transport. The owner discovers a public HTTPS endpoint, inspects its untrusted catalog, and persists selected tool definitions and fingerprints. Saving a connection never grants an agent permission to call it.

## Authority and catalog integrity

The configuration supports eight servers and twenty pinned tools per server. Pins include the tool's name, description, input schema and optional output schema. Canonical SHA-256 is checked when saving configuration and again against a fresh remote catalog before each call. The host provides selected, enabled catalog snapshots as explicitly untrusted agent context, so models can construct schema-valid requests without guessing IDs or making an unapproved discovery request.

`mcp_call` requires all of: the agent tool capability, account/task server selection, a separately authorized network origin, an enabled owner configuration, a matching tool pin, locally schema-valid arguments, and approval of the **exact external call**. `network.allow` does not bypass this approval. Task-scoped approvals bind the serialized request and a fingerprint of the owner configuration. Changing an endpoint or catalog invalidates prior and pending approval authority, including the execution-time recheck. The approval reason identifies the endpoint. Server annotations such as `readOnlyHint` never determine authority or risk. Remote service behavior is outside Relay's host sandbox; even a tool named `search` can have remote side effects.

`McpRegistry.configure` validates a complete configuration and aborts active operations on changed or removed servers. `configurations` and `agentCatalog` return copies. Task cancellation and emergency stop close active SDK clients and abort their requests. If a request was dispatched but its result is lost, invalid, interrupted, or reports an error, Relay uses `UNCERTAIN_TOOL_EFFECT`; automatic replay is blocked. A remote response is untrusted evidence of what that service reported, not proof of a host file, test, or side-effect rollback.

## Transport boundary

Only anonymous public HTTPS endpoints on port 443 are supported initially. There are no host stdio processes, OAuth redirects, provider credentials, cookies, arbitrary headers, private-network exceptions, legacy protocol fallbacks, sampling, elicitation, root sharing or subscriptions. Credentials embedded in the endpoint or common credential-shaped arguments are rejected; invalid requests are redacted before recording. This is a credential tripwire, not general DLP. Approval authorizes sending ordinary tool arguments to the selected remote endpoint.

`PinnedMcpSession` supplies the SDK's custom fetch implementation. It accepts POST JSON-RPC only at the exact configured URL and permits only discovery, tool listing and one tool invocation. It shares the research tool's public-address resolution, pinned connection lookup, actual connected-address comparison and explicitly verified TLS. Redirects and compressed responses are rejected. Protocol headers are allowlisted, and method metadata must match the JSON body. No server-controlled URL is followed, including authorization or resource links. Response headers such as cookies and authorization challenges are discarded.

Each operation has a thirty-second total lifetime, eight-request maximum, three catalog pages, fifty catalog tools, 64-KiB request ceiling and aggregate 512-KiB response ceiling. Output text is capped at 16 KiB with explicit truncation. Binary/resource output blocks are not fetched or executed; their omitted types are reported. Both JSON and finite SSE responses are accepted. SSE is buffered under the same total byte/time limit before SDK decoding: this adapter does not currently provide unbounded progress subscriptions or resume streams.

SDK version negotiation is explicitly pinned; it never silently falls back to an older transport. The transport independently forbids a second tool-call POST, even if SDK behavior changes. Input-required interactions are disabled, not automatically fulfilled. A server returning unsupported status codes, malformed data, or protocol/schema mismatches fails closed.

## Schema and resource limits

The SDK's maintained Ajv validator checks inputs and structured outputs. Relay first imposes a bounded JSON Schema subset: 16 KiB per schema, maximum depth ten, 256 nodes and arrays of at most 32 entries. Recursive/external references, regex/format validation and header-mirroring extensions are rejected. This sacrifices compatibility with some valid MCP schemas to keep untrusted compilation and validation bounded. Each compiled validator has a local cache; repeated hostile catalog changes do not accumulate in a global validator cache.

Ordinary JSON arguments have a 64-KiB bound, depth sixteen, and 4,096-node maximum. Prototype-related keys and non-JSON values are rejected. Owner-pinned schema validation adds the tool's own required/type/property constraints. No source text or server annotation can broaden the network or user grant.

## Research and validation

The owner opens **MCP tools** from phone navigation or the command palette. The browser clearly distinguishes discovery, contract review, saved-but-disabled configuration, and enabled configuration. Discovery sends the entered endpoint to the host; it does not grant execution. Descriptions and schemas are rendered as untrusted plain text, including markup-like strings. Selected contracts retain their complete metadata and fingerprint when saved. Availability labels describe configuration, not a successful connection test.

The task composer lists only enabled servers available to that account. Selecting one without its separately granted network origin displays a scope gap; it does not silently add a network permission. The account editor grants MCP server IDs independently from network, provider and workspace permissions. Unavailable saved grants remain visible so the owner can remove them deliberately. Owner management is lazy-loaded and absent from invited-user navigation. Provider keys are never part of these forms.

Browser tests use an explicitly intercepted discovery response with a real host-validated catalog fingerprint. Configuration, disabled-by-default persistence, explicit enabling, task options and account grants pass through the actual authenticated test host API and database. That browser fixture is distinct from SDK/transport integration tests and external interoperability acceptance.

The implementation follows the official [2026-07-28 transport specification](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx), the maintained [TypeScript client guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/clients/connect.md), and [SDK Streamable HTTP source](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/client/src/client/streamableHttp.ts). The choice to omit local processes, OAuth and private endpoints initially follows the concrete attack surfaces discussed in [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices); those features require separate security designs before enabling them.

Tests exercise the real official SDK with deterministic DNS/HTTPS responses: modern discovery, actual protocol requests, JSON and SSE results, source instruction isolation, exact-call approval, schema/description drift, malformed HTTP statuses, input validation, private destinations, redirects, byte limits, protocol downgrade, revocation, emergency stop and uncertain side effects without replay. These tests do not claim interoperability with every public server. A configured modern endpoint remains necessary for external integration acceptance; older or authenticated services are explicitly unsupported by this adapter.
