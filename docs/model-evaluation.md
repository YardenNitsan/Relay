# Versioned model capability evaluation

`server/models/evaluation.ts` implements **relay-capability-eval-v2**, a deterministic evaluation contract and bounded runner. The companion starter, durable store and Engine executor provide an explicit local-owner workflow using the existing scheduler and inference lease. It is a richer successor candidate to the original six elementary `relay-task-fit-v1` answers; the older calibration protocol and its stored records remain compatible. This implementation does not itself establish a measured routing-quality improvement.

The suite uses nine synthetic, public cases. No user conversation, document, credential or repository is a test fixture. Each call gets fresh messages and tools without another case's history or the grader's answer key.

| Case | Capability exercised | Deterministic outcome |
| --- | --- | --- |
| Dependency schedule | Multi-step reasoning | Completion times and critical path for a two-worker dependency graph |
| Loop boundary | Debugging | Defect location, exact replacement condition and predicted boundary results |
| Schema contract | Structured output | Typed fields, null handling, stable deduplication and no additional fields |
| Tool arguments | Tool proposal accuracy | Exactly one known function with exact permitted arguments |
| Document extraction | Extraction and calculation | Filter statuses and total amounts while treating a conflicting footer as data |
| Instruction boundaries | Format and instruction following | Exact two-line answer despite an untrusted conflicting quotation |
| Context revisions | Context handling | Highest revision of an asset among distracting records |
| Multilingual extraction | Hebrew, Spanish and English | Correct extracted counts and combined total |
| Failed tool recovery | Recovery proposal | Smaller allowed read-only retry after a synthetic failure receipt |

The debugging case predicts behavior; it **does not execute generated code**. The recovery case grades a proposed action after a fixture receipt; it is not a verified live recovery workflow. Tool cases never dispatch the proposed tool. Executable code tests, repository mutations and actual end-state verification require a separately approved sandbox/verifier integration. No host shell, `eval`, dynamic import, generated executable or unrestricted fallback is present.

The separate, opt-in [`relay-code-eval-v1` executable coding suite](code-evaluation.md) now provides three actual-output coding cases through the existing verified offline container boundary. It has distinct protocol/provenance records and explicit execution consent; the nine-case capability suite described here still never executes generated code. Missing sandbox prerequisites keep the executable suite unavailable before inference.

## Integration contract

`evaluationCases()` returns fresh input copies. `gradeEvaluationSample(caseId, output)` validates bounded text/tool output and grades exact structured outcomes. JSON object key order is irrelevant, while array order, value types, unexpected fields, wrong arguments and extra calls affect correctness. Text answers cannot claim that proposed tools succeeded. Deeply nested, malformed or oversized output fails the sample without executing it.

`runEvaluation(identity, executor, options)` invokes an injected executor sequentially. The complete suite must fit the call and context budgets before the first dispatch. Each case has a cancellation deadline (maximum 120 seconds); output allowance comes from the validated identity (256 to 2,048 tokens). Cancellation, timeout, executor failure or identity drift ends the suite. The runner aborts and joins executor cleanup before returning; a non-cooperative executor can delay termination, but must not cause admission to be released while it still runs. The runner cannot forcibly terminate that executor. It does not retry automatically.

`startModelEvaluation` requires a local owner principal, an available direct local model with tool support, known identity and safe admission. It creates a fast, read-only task with no workspace, host access, network or MCP grants; cloud sharing and financial allowance stay disabled. Its nine calls, output limit and active execution time are explicit. It records the request in `model_calibrations` before enqueueing. A failure to record that request cancels the task. Cloud benchmarking is not enabled.

`runLocalEvaluation` receives Engine's actual task slot, `ExecutionBudget`, `ExecutionActivity`, shared `LocalLease`, provider gateway, admission function and mandatory memory watchdog. It reacquires the shared lease for each case, checks fresh model/hardware identity, reserves each call through `Store.startCall`, streams with cancellation and pressure protection, and settles usage through `Store.finishCall`. It checks identity again before accepting the result. A non-overlapping one-second authorization watchdog stops lease waits or generation when the account, session, task, provider grant or emergency-stop state is revoked. Pending authorization checks and provider cleanup are joined before release. Tool requests are graded proposals; they are never forwarded to Relay's privileged tool broker. Local runtime default generation controls are not silently overridden.

Executor results include text, proposed calls, a verified completion boolean, actual execution identity and optional measured input/output tokens, first observed nonempty text latency (`firstContentMs`), provider-reported load time and peak RAM/VRAM. Missing measurements remain absent. New production reports do not write `firstTokenMs` or infer `generationMs` from token throughput; those optional fields remain readable for older v2 reports and do not establish an exact internal token timestamp. Model-call records separately retain available host-observed adapter load, stream and cleanup durations. Runner elapsed time includes executor overhead; it is not labelled generation throughput. A truncated or incomplete response cannot pass even if its partial text matches the answer.

## Evidence identity and trust

The strict identity includes model ID, provider, artifact digest, runtime and version, quantization, context limit, GPU offload mode, temperature, seed, reasoning choice, output limit, bounded extra execution settings and a hardware-configuration SHA-256 fingerprint. Missing/unknown artifact or runtime identity is rejected. `localEvaluationIdentity` fingerprints sanitized CPU/GPU configuration, driver, architecture and physical RAM, excluding hostnames, paths and changing available-memory readings. Runtime-default temperature and seed are represented as null (unset), not fabricated deterministic values. `runtime-auto` offload identifies an unset runtime-managed request; it does not claim a measured layer count. Explicit CPU/GPU settings remain distinct. Thus automatic runtime allocation and stochastic defaults remain limitations when comparing trials. For unquantized models use a known explicit representation such as `F16` or `unquantized`. Cloud models lacking verifiable artifact/runtime/hardware identity cannot supply comparable evidence through this contract. Current LM Studio discovery does not provide the required digest/runtime version and is rejected rather than assigned invented identity; verified Ollama metadata supports this path.

Every returned sample identity must match the requested identity exactly, with canonical object-key ordering. Evaluation version, exact case coverage, complete checklists, consistency of completion/pass states and measurement timestamp are validated when reading a report. Model aliases, changed artifacts, different runtimes, quantization, context, offload, reasoning, generation settings or hardware do not inherit scores.

Routing imposes a stronger offload requirement than report inspection: `runtime-auto` reports remain visible but contribute **no routing score**, even when two requested identity records match. An automatic request does not prove that separate loads used the same actual GPU placement. An explicit matching offload configuration can contribute evidence if every other identity field matches. Suites currently use runtime-default reasoning, so tasks requesting an explicit effort are also excluded; local Auto/default reasoning retains the evaluated runtime default. This conservative boundary remains until actual placement telemetry and effort-specific suites are available.

Reports distinguish `fixture` from `provider` execution. `evaluationEvidence` returns null for fixture reports, incomplete suites, duplicate/missing cases, unsupported versions, inconsistent scores, future timestamps or incompatible identities. It calculates category pass counts and overall success rate from validated samples. It does not authenticate arbitrary JSON: only host-generated, durably recorded reports may enter routing; neither model output nor client-uploaded reports are trusted measurement sources. No private model reasoning needs to be retained in this report.

`EvaluationStore.runAndRecord` is the only report-write path. It invokes the trusted executor itself and does not accept an arbitrary report or source label. Migration 6 adds account-scoped `model_evaluations` records. A unique task claim is stored **before** inference, preventing simultaneous duplicate runs and replay of a failed/interrupted attempt. Account/session/control/task authorization is checked before every case and before final persistence. Startup marks unfinished claims interrupted. A new explicitly requested task is required to repeat a benchmark.

The store exposes scoped `history(actor, limit)`, `report(actor, id)` and `evidence(actor, identity)` reads. History returns at most 40 metadata/score summaries; reports are limited to 64 KiB, and each account may retain at most 200 attempts. Capacity exhaustion rejects new attempts without deleting anything. Only completed, exact-identity provider reports can return scores; failed/interrupted attempts preserve status with no quality evidence. Raw model text and private continuation are not part of the evaluation report. Ordinary model-call auditing still follows the task retention policy.

There is one sample per capability and no statistical confidence claim. These tests are public and susceptible to memorization; passing is evidence about these cases, not broad intelligence or production reliability. Do not collapse their results into a universal quality score or allow them to bypass eligibility, permissions, hardware or financial constraints. Future changes to prompts, graders or case semantics require a new protocol version. Real improvement requires controlled comparisons against the old routing baseline using held-out representative tasks and actual verified outcomes.

## Research and verification

The design follows the distinction between observed outcomes, deterministic graders and isolated trials described in [Anthropic's official agent evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), checked 10 October 2026. It deliberately avoids adding a model-judge call to deterministic cases or adopting another service.

Focused verification uses `npm.cmd test -- tests/model-evaluation.test.ts tests/model-evaluation-store.test.ts tests/evaluation-runner.test.ts --maxWorkers=1`. Coverage includes graders, output boundaries, exact provenance/hardware fingerprints, fixture isolation, sequential execution, cancellation cleanup, durable claim duplication, per-account reads, revocation before dispatch and during generation, incomplete responses, interrupted history and retention capacity. Provider executors in these automated tests are fixtures: they test the real task/call/storage boundaries, not a real model's quality. No live local/cloud benchmark, paid request, sandbox execution or measured model-quality improvement was performed for this work.

`tests/evaluation-routing.test.ts` separately exercises real identity construction and compatibility against fixture repository/hardware inputs: matching automatic requests stay ineligible, matching explicit offload remains eligible, changed placement/artifact/runtime and explicit reasoning do not inherit scores, stale hardware is rejected and cloud candidates never read local evidence. These tests do not establish live model quality or measured GPU placement.
