# Native transport with a real isolated Relay host

12 October 2026. This closes the isolated JVM/native-transport-to-backend contract gate. It does not establish that the installed Android APK can reach a configured host through Android's trust store, the owner's LAN or Cloudflare Access.

## Verified command and result

Repository npm dependencies must already be installed with the lockfile and Node24+ available. From repository root:

```powershell
$env:JAVA_HOME='C:/Program Files/Android/Android Studio/jbr'
$env:ANDROID_HOME="$env:LOCALAPPDATA/Android/Sdk"
$env:RELAY_NATIVE_INTEGRATION='1'
./android/gradlew.bat -p android :app:testDebugUnitTest --console=plain
Remove-Item Env:RELAY_NATIVE_INTEGRATION
```

Final run: exit0, `BUILD SUCCESSFUL in 18s`; **20 tests across6 classes,0 failures,0 errors,0 skips**. The real-host scenario takes3.211seconds. `npm.cmd run typecheck` also passes for the fixture. No assembly or production-runtime change was required. The delivered APK still hashes to `9c253dc1e642d4b41ad4def9d4cf9a8f2ca42362c34172bf8452881b69733a8f`.

Without `RELAY_NATIVE_INTEGRATION=1`, this one scenario is intentionally skipped; ordinary native tests do not implicitly download/start the Node host. Gradle tracks the opt-in value and relevant host/shared/fixture source as test inputs, so switching modes or modifying those contracts invalidates the test result cache. Android CI needs an explicit Node/npm dependency setup and opt-in step before its result can be called real-host integration acceptance.

## Test boundaries

`android/app/src/test/java/app/relay/nativeclient/LanIntegrationTest.kt` starts `scripts/native-lan-fixture.ts` as a child process through private pipes. The fixture is never imported by a production entry point and refuses to run without its explicit test argument. Its database is a new in-memory PostgreSQL instance. Its managed files reside in a uniquely created temporary directory; cleanup verifies the resolved directory is directly beneath the actual OS temporary root and has the expected fixture prefix before deletion.

The fixture runs the actual `createApp`, `Store`, `Sessions`, `LocalPairing`, account authorization, `ToolBroker` and `Engine` implementations. An unbound owner application performs real pairing and owner account/invitation/revocation operations through Fastify injection; it does not open owner port4317. The native client connects over a real HTTPS socket to the separate LAN application on127.0.0.1 and a random ephemeral port. Reserved4317/4318/4319/4323 ports are excluded. There are no added HTTP control routes or authentication middleware substitutions.

An ephemeral certificate/key is generated by the JVM and passed through stdin; the invitation returns through the private stdout reader. Neither is logged or written as an artifact. Test-only reflection derives a client from the production OkHttp builder and supplies the specific test CA and `relay.test`→127.0.0.1 DNS resolution. Hostname/certificate verification, Origin, cookie, CSRF, redirects, session policy and response parsing remain real. Android system trust, production private-interface selection, certificate-file ACLs and deployment configuration parsing are intentionally outside this harness; loopback direct app construction must never be copied into production listener setup.

All provider connections are disabled, provider fetch refuses network, keyring access is disabled and fixture secrets use an empty environment. Tasks exercise real admission, history, lifecycle/cancellation and durable events without invoking a model. No generated answer, model quality or agent execution success is claimed. File contents are explicitly synthetic test data uploaded through the real authenticated workspace endpoint.

The test confirms shutdown acknowledgement and a zero child exit code. The fixture closes app streams/listeners, owner application, engine and database before deleting its workspace, including startup-error cleanup after resources are acquired. It has a bounded120second lifetime and cleans up when its parent pipe closes. The final run left no `relay-native-lan-*` temporary directory.

## Remote authentication blocker

Cloudflare [Managed OAuth](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/managed-oauth/) documents a supported public-client authorization-code/PKCE approach; [agent authentication guidance](https://developers.cloudflare.com/cloudflare-one/access-controls/authenticate-agents/) describes discovery and resource binding. Those documents were inspected during the architecture audit. No live deployment setting was inspected or changed here.

Internal implementation is still missing: system-browser OAuth, PKCE/state transaction handling, token lifecycle and a verified HTTPS Android App Link callback. External configuration/proof needed: the actual Access application must support/enable Managed OAuth, authorize the public native client and exact resource/redirect URI, serve the callback-domain association for the actual package/signing certificate, and prove that an accepted bearer produces the existing signed human Access assertion at the Worker while preserving Relay account approval and CSRF. The current Worker denies arbitrary callback/association paths; a reviewed supported callback arrangement is needed before deployment changes. Existing browser SSO cookies, a shared service token, a WebView or an unprotected alternate host are not substitutes.

Until both implementation and configuration are proven, native remote Access remains unavailable. This isolated LAN test supplies no Cloudflare token or Access bypass and makes no public endpoint.
